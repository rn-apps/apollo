# S2.7.1 — Home shows API reachability

Brief for [S2.7.1](../F2.7-connected-home.md#s271-home-shows-api-reachability),
at `f3afca4`.

## Goal

Replace the scaffold's item-count page with a dark, branded Apollo home that
calls the API's `GET /livez` once on load and once per Retry, and shows
Connecting, API connected or API unavailable.

## Settled

- The liveness response is the kit's: `GET /livez` returns `200` with
  `{"status":"pass"}`. Anything else (a non-2xx status, a network failure, or
  a body whose `status` is not exactly `"pass"`) is API unavailable.
- The request is same-origin, to the relative URL `/livez`. The dev-server proxy
  forwards `/livez` to `http://localhost:8000`, as it does `/v1`.
- The logo is the old app's mark, `rn_backup/apollo/apps/web/static/icon.svg`,
  copied verbatim below. It is the favicon and the logo on the page.
- ngkit has no button or status primitive yet. This page uses a native
  `<button>` and plain markup styled with Tailwind's semantic colour utilities
  from ng-tailwind's bridge. No E3 primitive is needed for this checkpoint;
  F2.5 brings the shell.
- Colour literals live only in `apps/web/src/styles/theme-apollo.css`. The
  existing `S2.4.1: no colour literals` spec scans
  `src/app/**/*.{ts,html,scss}` and must stay green, so the logo is an `<img>`
  of `icon.svg`, never inline SVG in a template.

## Current behaviour

- `apps/web/src/app/app.ts` (`App`, selector `app-root`) requests
  `GET /v1/items` in `ngOnInit` and renders "API connected: N items" or the
  problem detail, under an `<h1>` reading `apollo`. It declares `ItemsPage`
  and `Problem` interfaces, used nowhere else. It has no `changeDetection`.
- `apps/web/src/app/app.spec.ts` holds two specs for that behaviour, using
  `provideHttpClient()` and `provideHttpClientTesting()`. The app is zoneless
  (Angular 22); specs settle with `await fixture.whenStable()`.
- `apps/web/proxy.conf.json` proxies only `/v1`.
- `apps/web/src/index.html` has `<title>web</title>` and links `favicon.ico`
  (Angular's default icon, in `apps/web/public/`).
- With the new specs written and the old component unchanged, each spec fails at
  `http.expectOne('/livez')` with "Expected one matching request for criteria
  "Match URL: /livez", found none." (`HttpTestingController.verify()` also
  reports the unmatched `/v1/items` request).

## Tests first

Replace the whole of `apps/web/src/app/app.spec.ts`. Keep the existing `TestBed`
setup (`imports: [App]`, `provideHttpClient()`, `provideHttpClientTesting()`,
`afterEach(() => http.verify())`). Read the status from
`[data-testid="api-status"]` and the button from `[data-testid="retry"]`. After
each `flush` or `error`, `await fixture.whenStable()` before asserting. Every
test title starts with `S2.7.1:`.

- `S2.7.1: shows the Apollo brand`: `h1` text is `Apollo`; an `img` has `src`
  `icon.svg`. Flush `/livez` with `{ status: 'pass' }` so `verify()` passes.
- `S2.7.1: reflects API reachability — Connecting before the response`: after
  the first `detectChanges()`, before flushing, the status text is
  `Connecting…` and there is no Retry button. Then flush `{ status: 'pass' }`.
- `S2.7.1: reflects API reachability — connected on 200 pass`: flush
  `{ status: 'pass' }`; the status is `API connected`; no Retry button.
- `S2.7.1: reflects API reachability — unavailable on a request failure`:
  `req.error(new ProgressEvent('error'))`; the status is `API unavailable`;
  the Retry button is present.
- `S2.7.1: reflects API reachability — unavailable on a 503`: flush
  `{ status: 'fail' }` with
  `{ status: 503, statusText: 'Service Unavailable' }`; the status is
  `API unavailable`.
- `S2.7.1: reflects API reachability — unavailable on an unexpected payload`:
  flush `{ status: 'ok' }` with status 200; the status is `API unavailable`.
- `S2.7.1: reflects API reachability — Retry recovers`: fail the first request
  with `ProgressEvent('error')`; click Retry; assert the status is
  `Connecting…`; `expectOne('/livez')` matches a second, new request; flush it
  with `{ status: 'pass' }`; the status is `API connected` and the Retry
  button is gone.

Each test asserts `expectOne('/livez')` with method `GET`. Before the change all
of them fail as "Current behaviour" says.
