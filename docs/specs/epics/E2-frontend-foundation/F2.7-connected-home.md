The first runnable Apollo page is a dark, branded Angular home that shows
whether the local FastAPI process responds.

## Design

Use the existing Angular and FastAPI dev tasks. The Angular proxy forwards
`/livez` to the same API as `/v1`. The home uses the kit's existing liveness
response and makes one same-origin request on load and one per Retry. Liveness
only measures API reachability. Library readiness and capabilities arrive with
[F1.7](../E1-backend-foundation/F1.7-status-and-capabilities.md).

Use an existing Apollo logo if available. Otherwise use a simple Apollo wordmark
and a matching favicon. The home uses the theme from F2.4 and replaces the
scaffold item count. The full navigation shell and dashboard follow in
[F2.5](F2.5-shell-and-routes.md) and
[F12.1](../E12-home-status-settings/F12.1-home-dashboard.md).

## S2.7.1 — Home shows API reachability

**State:** Closed (2026-11-19)

**Acceptance:**

- `/` shows the Apollo brand and dark theme. The browser tab displays the Apollo
  title and favicon. The home loads at 1280 px and at a narrow viewport.
- `S2.7.1: reflects API reachability`: the Angular spec checks the initial
  Connecting state, API connected on `200` with `{"status":"pass"}`, and API
  unavailable on a request failure or unexpected payload. Retrying after a
  failure issues a new request and recovers to API connected when it succeeds.
- With `task api:dev` and `task web:dev` running, the browser receives the real
  `/livez` response through the web origin and shows API connected. Stop the
  API and reload to see API unavailable. Restart the API and use Retry to
  reconnect without reloading the page.
