# ADR-0008 — One server-sent event stream carries live state, re-derived from the database, with no replay

**Status:** proposed (2026-11-15) · **Scope:** how the UI learns of job progress
and app status

## Decision

The app has one SSE connection, `GET /v1/events`. It carries job frames and a
status frame (health, error counts, track counts, worker state). The shell opens
it once and never polls.

- **State-derived.** Each tick (500 ms), the stream re-reads current job state
  from `apollo.db` and emits what changed. On connect it emits every
  non-terminal job, and terminal jobs are seeded silently, so they set the
  baseline without emitting a frame.
- **No `Last-Event-ID` replay.** A reconnect is told the current truth, which is
  worth more than the intermediate progress it missed. The `id:` field is
  still sent, for ordering only.
- Framing, heartbeat, retry and the terminal error frame come from
  `rn_forge.fastapi.sse.sse_response`. The client is ngkit's event stream,
  which keeps the browser's own reconnect and backs off only once the
  connection is `CLOSED`.
- A terminal job frame invalidates the client resources that job affects,
  through ngkit's resource invalidation.

## Consequences

- A new event type follows the same model: current state on connect, no replay.
- One stream means one place to test ordering and reconnect, and one connection
  per browser tab.
- At 500 ms a tick costs one indexed query on `job`, plus a status read that is
  served from snapshots ([ADR-0006](ADR-0006.md)).

## Alternatives considered

- **Event-sourced stream with replay.** It needs an event log and retention for
  intermediate progress that nobody reads.
- **Polling per screen.** The old app removed polling because several screens
  each polled the same state.
- **WebSockets.** The traffic only flows from server to client, and the kit
  already ships SSE (pykit F6.2, ngkit E15).

## Background
