# ADR-0006 — Full-library reads are served from actor-built snapshots, discarded on mutation

**Status:** proposed (2026-11-15) · **Scope:** any read that walks the whole
beets index

## Decision

A read that needs the whole index is built once, on the actor, as an in-memory
**snapshot** and served from it until a mutation discards it. Album summaries
with their member index, facets and library stats are such reads.

- One snapshot type, generic over its value. Rebuilding is lazy, and when
  several callers ask during a rebuild they share it, so there is one rebuild
  per wave.
- Snapshots are invalidated when a job that mutates the library reaches a
  terminal state, and on the single-item paths that write tags: edit, proposal
  accept and promotion.
- A snapshot is derived from beets, not a second source of truth, and is never
  persisted.

## Consequences

- A new full-library projection uses the snapshot type. It does not walk the
  index per request.
- Every job type declares whether it mutates the library, which decides
  invalidation. A wrong declaration shows stale data until the next mutation.
- The first read after an invalidation pays the full walk. On the old app that
  walk took about 2.6 s at 12,335 tracks.

## Alternatives considered

- **A persistent `track_read` table in `apollo.db`** that mirrors the index for
  list, sort and filter queries. It takes reads off the actor completely, but
  puts a second copy of every tag on disk that has to be kept in step. It
  stays deferred until the acceptance run measures a need for it.
- **No cache.** `/albums` cost 2.45 s per request on the real library.

## Background

Restates old apollo ADR-0009 (recorded 2026-08-31; originally I35). Its
measurement was `/albums` falling from 2.45 s to 0.9 ms after the change.
